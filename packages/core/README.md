# @codechart/core

The engine shared by the [codechart CLI](https://www.npmjs.com/package/codechart) and the codechart desktop app.

It is the part both products must agree on:

- **Specs** — the map, flow, business, release and explain schemas, their zod validation and generated JSON schemas.
- **Truth checks** — anchor reading, mention checks and the checks that compare a claim with the code and the git diff; map layout (elkjs).
- **Git rules** — changed files, log, preview and diff, and which diagram a change should produce.
- **Review notes** — the note format, parser, merge, carry-over and storage, plus shared page and review file naming.
- **Config** — the `.codechart.yaml` schema, loader and repo-root lookup, and `writePinned`, which writes the `map.pinned` names sorted by id and leaves the rest of the file as it was.
- **Code layer** — reads a repo's files, their symbols (classes, functions, methods, types) and their calls with tree-sitter, for TypeScript, JavaScript and Python. `parseRepo` reads a whole repo, `parseCode` one file, and `openCodeIndex` keeps one repo current: a save re-parses only the files whose content hash changed, then re-matches only the code another file's change can reach (reverse indexes for imports and names); a file with a syntax error keeps its last good symbols, and the last good imports and export names its text still names. Imports resolve to repo files (relative paths, tsconfig `paths`, package `exports` and `imports`, npm, yarn and pnpm workspaces mapped to their source) and imported names are followed through barrel files to where they're defined; an import nothing proves is `unknown`, a package outside the repo `external`. A call is `resolved` only when a resolved import or a same-file definition reaches its function; otherwise it is `name-only`. Python imports resolve following CPython's path finder over the project's source roots (`src/` for files under it; `src/` and the project root for the rest); a module found nowhere in the repo is `external`, and in a file that edits `sys.path`, absolute imports of non-stdlib modules are `unknown`. Files without imports get entities and references instead:
  - Entities: SQL `CREATE TABLE`s, Prisma `model`s, `enum`s, `view`s and composite `type`s (`schema.prisma` and every `.prisma` file of a multi-file schema), the jobs and steps of `.github/workflows` files, docker-compose services, `package.json` scripts, and Bash functions (as symbols).
  - References: the files workflow `run` steps and npm scripts run, Bash `source` and `.`, HTML `<script src>` and `<link href>`, and CSS `@import`; and Prisma relations, from a model to the model a field's type names (`to` holds that model's id); the side that holds the foreign key has `foreignKey`: its key fields, the fields they reference and the range of the `@relation(fields: […], references: […])` that states them. A relation is `resolved` only when the same file declares that model; a type no declaration in the file names stays `unknown` with no file, since one file can't prove which schema folder it belongs to (known limit: in a multi-file schema it may be another file's model, enum or composite type).
  - A reference is `resolved` only to a file of the code layer, and only where its folder is fixed: the page or stylesheet's folder, the package folder for npm scripts, the step's working directory after an `actions/checkout` of the repo, or the script's own folder written with `dirname "$0"` or `BASH_SOURCE`. A URL is `external`, and anything else is `unknown`.
  - `createResolver`, `linkImports` and `linkCode` re-resolve without re-parsing.
  - Patterns: `checkPattern(grammar, pattern)` says why a [tree-sitter query](https://tree-sitter.github.io/tree-sitter/using-parsers/queries/) can't be a map rule's pattern (syntax, unknown node type or field, no `@entity` capture or more than one, a predicate other than the `eq?`, `match?` and `any-of?` families, which filter), with line and column. `compilePatterns([{ id, grammar, pattern }], { id, timeoutMs })` checks the same, then compiles one query per grammar into a named set (`id`, default `patterns`). Pass one set or several as `patterns` to `parseCode`, `parseRepo` or `openCodeIndex`: each set runs on its own, within its own limits, so the app's built-in set keeps all its matches when a slow user set is cut off; two sets in one parse need two ids. Each file gets `matches`: `{ set, pattern, range, hash, captures }` per set, pattern and `@entity` node, sorted by position, then set and pattern order. `range` points at the code, `hash` is the sha256 of its text, and `captures` holds the text of the other captures by name (the first node of each; names starting with `_` are left out); the source text itself is not kept. The patterns run on the tree the parse already made, so a save is parsed once. A grammar is the one core reads the file with (`patternGrammarOf`): `typescript` for `.ts`, `.mts` and `.cts`, `tsx` for `.tsx`, `javascript` for `.js`, `.mjs`, `.cjs` and `.jsx`, then `python`, `html`, `css`, `sql`, `bash`, `yaml`, `json` and `prisma`. While a file has a syntax error, its matches follow symbols (Live map #11). Per group of identical matches (same set, pattern and hash), the current matches and those of the last good parse are paired one to one: as many pairs as possible, then the least total distance between their starts, a start read as one number in which a line outweighs any column: line × (widest column in the group + 1) + column, so a minified line of any length stays line-major. A paired current match is shown at its current place; an unpaired one only when no error touches it, so nothing new comes from broken text; a last good match left unpaired is kept at its old place, marked `kept`; a paired one is not shown, so no stale copy stands next to its current one. A generated test checks this against a brute-force oracle. Cost: linear for matches still at their place; the rest O(s × (d + 1)) per group, s the smaller and d the difference of the two counts left, from a budget of a million steps per parse shared by all groups; a group past what is left of it, or whose largest possible total would pass `Number.MAX_SAFE_INTEGER`, gets a linear nearest-first pairing that may pick a worse pairing but keeps the guarantees: every match of the smaller side pairs, the counts are the same, and no kept copy stands where a current one is. Each set's query stops after its `timeoutMs` (default 500) on a file, which then gets `patternLimits: { [set id]: 'timeout' }` with the matches found so far; `'match-limit'`, best effort, when tree-sitter dropped matches past `matchLimit` (web-tree-sitter shares one query cursor per process whose pool only grows, so whether a file hits it depends on what ran before; the time limit is the bound). A set holds WebAssembly memory: `delete()` it once nothing parses with it.
- **Agent presets** — the agents codechart knows, their skill folders, and commander-free helpers to install and remove the skill.

The CLI owns everything that talks to a user or an agent: commands, terminal and HTML renderers, PR maps, the update check and the OpenCode plugin.

## Stability

Version `0.x`: the API may change between minor versions. The app pins a version (`"@codechart/core": "0.1.x"`) so it stays on a range it was built and tested against.

## Usage

```ts
import { validateSpec, checkMapNodes, layoutSpec, loadConfig, parseRepo, openCodeIndex } from '@codechart/core';
```

Node 22.12 or later, ESM.
